# RealityLoop agent instructions

RealityLoop is a standalone, customer-owned simulation/verification repository and Git submodule. **Always use the real Taskyon Design Graph node engine internally**, but never require Taskyon UI, account, services, Space or P2P to simulate, cache or evaluate.

## Git identity

- Commit as `Thomas Rose Meschede <thomas.meschede@xyntopia.com>` for both author and committer. Never use an AI identity such as `OpenAI Assistant <assistant@local.invalid>`, `Codex`, a model or vendor name, or an AI attribution trailer; history must show who is responsible for the change. Verify with `git log -1 --format='%an <%ae> | %cn <%ce>'` before pushing.

- `src/dag-nodes.ts` defines the canonical `RealityLoop.Scenario → Simulation → Metrics/Observations` Taskyon DAG nodes. Node/CLI runs use local `src/dag.ts` and `src/dag-storage.ts` to persist the exact Taskyon graph/invocation/run/project schemas with SHA-256 artifacts. Browser examples use the same nodes, with in-memory caching pending durable browser persistence.
- The bundle `src/vendor/taskyon-comp-dag.mjs` is generated from canonical `frontend/packages/comp-dag` and pinned by `src/vendor/taskyon-comp-dag.lock.json`. Never write a new DAG runtime or invent a parallel identity scheme. Source checkout needed only when regenerating, not when running.
- P2P should only be optional transport for explicitly permitted artifact synchronization/import into Taskyon UI. It is never a physics or graph execution dependency. No ambient Space credentials or unauthorized StorageClient write authority.
- Default supermarket physics is Rumoca Modelica with five fixed-box analytic contacts and ~0.18 m projected swept clearance; CI gates at ≥0.10 m and negligible penetration. An opt-in Modelica GLB mesh mode uses a replaceable function and 3D sphere-to-solid-mesh queries with the same contact forces and Modelica dynamics. Both are simplified robot-envelope approximations, not real-world safety validation. Rapier remains optional, never the default.
- Modelica's opt-in `external "C"` scalar real3 callback queries either Rapier or MuJoCo WASM from inside patched Rumoca (`src/modelica/external-host.ts`, `src/modelica/supermarket-external.ts`). The model-level `replaceable`/ `redeclare` function mechanism works; the stock browser runtime is Modelica-only and the generalized native `ExternalObject`/record/array ABI is still unsupported. External callbacks currently return scalar penetration while normals come from Modelica geometry; never run Rapier or MuJoCo's physics steppers inside the Modelica host.
- Sensor data is synthetic: 5 multi-elevation LiDARs, PCL ICP scan-registration/2D map, rendered front RGB, IMU/encoder, other camera metadata. It is not production SLAM, camera calibration or BrainOS.
- The canonical supermarket physical-geometry source is `assets/meshes/supermarket-layout.json`. `npm run build:collision-assets` regenerates the GLB, `src/generated/supermarket-obstacles.ts` and `modelica/RealityLoopImportedCollision.mo` (3D vertices, faces, body offsets, BVH) from that asset. `npm run check:collision-assets` fails if generated files are stale. `src/geometry.ts` exposes the generated layout to LiDAR, Three.js and backends; `src/modelica/scene.ts` injects it into the Modelica world. `modelica/RealityLoopCollision.mo` contains compiled analytic and sphere/triangle/closed-solid narrow phases; the optional mesh-backed supermarket redeclares its contact query but retains Modelica vehicle dynamics. For other assets, `npm run compile:collision-mesh -- file.obj Output.mo --solid` creates deterministic Modelica geometry plus hashed provenance. Untagged GLBs need explicit `--all-meshes`; concave/nonplanar OBJ n-gons must be triangulated first. A BVH accelerates candidate queries but has no demonstrated speedup on small 12-triangle boxes. Full mesh-vs-mesh contact, convex decomposition and contact manifolds are not implemented. Never approximate an arbitrary mesh as an AABB without consent. Do not silently export supermarket LiDAR/camera data for other worlds.
- `src/solar-plant.ts` is a deterministic reduced-order PV/BESS model: solar position, plane-of-array irradiance, temperature derating, inverter clipping, energy accounting, bounded battery dispatch. It reuses equipment-envelope dimensions, orientation conventions and instanced-placement concepts from Joulios `feature/darden-study` (`src/modules/packing/layout3dScene.ts` and `joulios/graph/nodes/HybridPlantLayoutOptimizerNode.ts`) without taking a runtime dependency or claiming a Darden as-built. `viewer/power-plant-scene.ts` and `viewer/solar-ground.ts` provide visual-only PBR panels, support frames, inverter/BESS yard, solar sky and shadows. Do not conflate the visual sun shadows with a validated irradiance/shading solver. Keep the source dimension mapping explicit; solar output must pass strict power balance, SOC bounds, grid export limits and tracker comparisons. Run `npm run check:browser:solar` against a Pages build and `npm run capture:solar` when updating the original gallery screenshot.
- `src/mission-experiments.ts` defines three bounded mission examples through the same Taskyon DAG nodes: modular 40 cm satellite **reduced-order** Euler/reaction-wheel ADCS, a Mars terrain rover, and a construction delivery robot. The satellite now combines separately compiled `modelica/KeplerFormation.mo` **two-body Keplerian orbital-element** chief/servicer position and analytic velocity states (`src/orbital-formation.ts`) with ADCS samples on matching timestamps. Always transform relative ECI positions into the chief RTN frame using analytic ECI velocity (not a finite difference) and position Earth on negative RTN radial, not ECI XYZ. `src/orbital-inspection.ts` generates synthetic 2D silhouette range scans from geometry shared with `viewer/mission-scene.ts` through `src/satellite-scan-geometry.ts` and bounded planar ICP from a coarse pose prior, full 3D body-quaternion transforms, and synthetic noisy relative odometry; its own observation stream is exported independently from supermarket LiDAR. This is not 6DoF spacecraft SLAM, J2/drag-accurate flight mechanics, real calibrated sensors, thrust control, docking guidance or orbital hazard avoidance. `viewer/mission-scene.ts` presents the chief/servicer and Earth with intentionally compressed sizes and separate hardware-only SSAO. `viewer/mars-habitat.ts` and `viewer/mars-materials.ts` present procedural regolith, static contact AO, habitat, decorative arms and support robots; only the Mars traversing rover follows the reduced-order physics, not the extra geometry. Do not claim flight-qualified docking, accurate regolith/suspension, simulated Mars sensors or safety-certified construction navigation. Run `npm run check:browser:missions` after the Pages build, and capture gallery screenshots with `npm run capture:missions`.
- Require explicit source/asset digests, solver/timestep/seeds, bounded execution and artifact replay checks. A cache hit is **not** independent replay verification; run `realityloop verify <invocation-id> [store-dir]` to check recorded Taskyon artifacts and recompute in a new DAG store. Current local graph store is single-writer only. Byte-integrity hashes alone are not proof of cross-platform bit-exact physics.
