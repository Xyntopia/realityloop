# RealityLoop agent instructions

RealityLoop is a standalone, customer-owned simulation/verification repository and Git submodule. **Always use the real Taskyon Design Graph node engine internally**, but never require Taskyon UI, account, services, Space or P2P to simulate, cache or evaluate.

- `src/dag-nodes.ts` defines the canonical `RealityLoop.Scenario → Simulation → Metrics/Observations` Taskyon DAG nodes. Node/CLI runs use local `src/dag.ts` and `src/dag-storage.ts` to persist the exact Taskyon graph/invocation/run/project schemas with SHA-256 artifacts. Browser examples use the same nodes, with in-memory caching pending durable browser persistence.
- The bundle `src/vendor/taskyon-comp-dag.mjs` is generated from canonical `frontend/packages/comp-dag` and pinned by `src/vendor/taskyon-comp-dag.lock.json`. Never write a new DAG runtime or invent a parallel identity scheme. Source checkout needed only when regenerating, not when running.
- P2P should only be optional transport for explicitly permitted artifact synchronization/import into Taskyon UI. It is never a physics or graph execution dependency. No ambient Space credentials or unauthorized StorageClient write authority.
- Default supermarket physics is Rumoca Modelica with five fixed box contacts and ~0.18 m projected swept clearance; CI gates at ≥0.10 m and negligible penetration. This 2D approximation is not real-world safety validation. Rapier is comparison-only and optional.
- Modelica's limited opt-in `external "C"` scalar callback can query MuJoCo WASM from within the patched Rumoca solver; the full native `ExternalObject`/array ABI is not linked. Default supermarket remains analytic contacts. No duplicate MuJoCo physics time stepping.
- Sensor data is synthetic: 5 multi-elevation LiDARs, PCL ICP scan-registration/2D map, rendered front RGB, IMU/encoder, other camera metadata. It is not production SLAM, camera calibration or BrainOS.
- `src/geometry.ts` is the canonical supermarket obstacle source. `src/modelica/scene.ts` injects it into Modelica; supermarket LiDAR, renderer and MuJoCo read that same geometry. Other worlds must have their own explicit terrain/obstacle definitions and sensor models; do not silently export supermarket LiDAR/camera data for unrelated worlds.
- `src/mission-experiments.ts` defines four runnable, bounded **reduced-order** examples through the same Taskyon DAG nodes: modular 40 cm satellite ADCS (mass/inertia tensor + reaction wheels), iBOSS-inspired translational soft capture, a Mars terrain rover with candidate mass/power constraints, and an exclusion-zone construction-site delivery robot. Their original procedural Three.js scenes live in `viewer/mission-scene.ts`; `viewer/mars-habitat.ts` builds the original modular habitat, assembly arms, support robots, atmospheric terrain and sand normal maps. The Mars traversing rover is simulated; manipulator, habitat and support robot animation is visualization-only and is not part of collision/sensor calculations. Preserve that distinction in any user-facing copy. Do not claim orbit propagation, flight-qualified docking, accurate regolith/suspension, real sensor streams or safety-certified construction navigation. Run `npm run check:browser:missions` after a Pages build; regenerate the four gallery previews using `npm run capture:missions`.
- Require explicit source/asset digests, solver/timestep/seeds, bounded execution and artifact replay checks. A cache hit is **not** independent replay verification; run `realityloop verify <invocation-id> [store-dir]` to check recorded Taskyon artifacts and recompute in a new DAG store. Current local graph store is single-writer only. Byte-integrity hashes alone are not proof of cross-platform bit-exact physics.
- Headless and browser experiments must use DAG nodes. The implemented `RealityLoop.OfflineVideo` derivative consumes an immutable recorded simulation artifact via `realityloop video`, streams browser-free RGB diagnostic frames to FFmpeg/H.264, and records a new DAG invocation/manifest/content hash; it never reruns physics. Keep offline PBR render capture as a distinct optional future backend.
- Keep the future async/streaming optimization DAG proposal **deferred research**, no release or architecture agreed. Do not expand this during normal simulation work.
- Static robot body panels and fixed wheels/mounts may be batched by material in `viewer/static-robot-batcher.ts` to reduce draw calls, but never batch future articulated parts that need independent animation. The actual robot root pose, LiDAR extrinsics, physics and observation outputs remain unchanged. Decorative pallet cartons must stay inside the canonical blocker AABB (`tests/supermarket-decor.test.ts`); the distant painted cooler wall is outside the robot goal area and must never be described as a LiDAR-observable obstacle. Production previews may show procedurally rendered scenes, never third-party development reference photography.
- Development-only visual comparison is permitted: an agent may look at an external image to improve the independently authored scene's camera composition, shelf density, product colors, ceiling fixture layout, material response, and lighting. Such imagery is a transient private development aid: keep downloads and comparisons **outside every Git checkout and build artifact**, never commit or publish the images, and do not add identifying filenames, source URLs, authors, credit, image IDs, or references to such aids to source comments, Git commits, README, agent handoffs, system definitions, tests, or release notes. Make all final assets original/procedural or separately licensed, and verify the produced scene against rendered app screenshots. Do not copy protected logos/product packaging or imply an image is an original simulator capture.
- Keep PBR visuals strictly separate from canonical obstacle geometry. `viewer/supermarket-products.ts` provides 24 original SKU designs and 1,440 decorative indexed-batch product transforms in four shared-atlas packaging groups, 40 price strips, optional caps and one-draw-call performance LOD; `viewer/supermarket-interior.ts` uses bundled CC0 Poly Haven diffuse/normal/roughness textures for the floor. External photography can guide development privately, but **do not commit external reference photos, author names, source URLs, photo IDs, attribution/reference documents, or copies of development comparisons**. The standalone aisle view hides only display diagnostics; hiding panels must suppress the extra RGB preview WebGL pass, not sensor/DAG observations. Real GPU FPS must be measured; Chromium software rendering ~1–2 FPS is not acceptable for real-time operation. Verify `npm run check && npm test && npm run build && npm run build:web` and browser interaction/renderer errors before delivery. Never commit generated runs, secrets or reference supermarket photos.
